# 多平台攻略聚合与个性化方案定制页设计

## 1. 目标与边界

### 目标

把用户在定制页填写的城市、日期、预算、偏好和特殊需求，转化为一次可解释的攻略聚合流程。本设计只覆盖 **小红书 + 抖音** 两个来源，百度不纳入采集范围。

1. 从小红书、抖音收集公开攻略；
2. 统一成同一种数据结构；
3. 去重、对齐景点与路线；
4. 按用户约束和证据质量评分；
5. 输出 2–3 个可比较的方案；
6. 每个推荐理由都能回溯到具体平台、内容和时间。

### 非目标

- 不伪造平台内容、点赞数或作者信息；
- 不绕过平台登录、验证码、风控或付费墙；
- 不保存完整攻略正文，只保存必要摘要、结构化结论与来源链接；
- 平台不可用时，不静默用模型编造“平台推荐”，而是明确标注“通用建议”。

## 2. 核心流程

```text
需求采集
  ↓
平台与授权检查
  ↓
多平台检索（并行）
  ↓
原始内容入库（SourceRecord）
  ↓
统一解析与结构化（GuideClaim）
  ↓
跨平台去重与聚类（GuideCluster）
  ↓
候选方案生成（PlanCandidate）
  ↓
硬约束过滤 + 综合评分
  ↓
对比页展示 + 推荐理由
  ↓
用户选择/调整
  ↓
生成最终行程并写入来源引用
```

### 2.1 需求采集

复用现有定制页 Step 1–3：

- 目的地/多城市与停留天数；
- 日期、预算、是否含城际交通；
- 交通、住宿、兴趣偏好；
- 特殊需求（想去的景点、老人/儿童、饮食禁忌等）；
- 新增“攻略来源”选择：小红书 / 抖音，可多选。

### 2.2 平台检索

为每个平台生成独立查询：

```text
城市 + 兴趣关键词 + 旅行天数 + 季节 + “攻略/避坑/路线”
```

各平台并行执行，单平台超时或失败不阻塞其他平台。

### 2.3 统一结构化

平台原始内容统一转换为：

- 地点/景点；
- 建议顺序与路线；
- 建议停留时间；
- 预算区间；
- 预约/闭馆/交通提示；
- 适合人群/季节；
- 引用片段与来源。

### 2.4 去重与聚类

同一景点或同一路线在不同平台可能名称不同：

- 名称归一：去除“景区/风景区/公园”等后缀；
- 别名归并：夫子庙 / 南京夫子庙 / 夫子庙秦淮风光带；
- 坐标距离阈值内合并；
- 保留每个平台的独立来源，不因合并丢失出处。

### 2.5 候选方案与筛选

先过硬约束，再算综合分：

- 日期/季节是否可行；
- 是否包含用户“想去”的点；
- 预算是否超限；
- 体力/亲子/老人限制；
- 平台来源是否足够。

输出 2–3 个方案，例如：

- 经典全覆盖；
- 轻松慢游；
- 小众深度。

### 2.6 最终输出

用户选中方案后：

- 生成完整每日行程；
- 每个景点/餐饮/交通建议带 `source_refs`；
- 结果页可展开“为什么推荐”；
- 可回到对比页更换方案。

## 3. 页面信息架构

### 桌面端三栏

```text
┌──────────────────────────────────────────────────────────────┐
│ 行程摘要：南京 · 3天2晚 · 2人 · 预算 ¥3000 · 偏好 历史/美食   │
│ 步骤：1 需求  →  2 来源  →  3 聚合  →  4 对比  →  5 生成      │
├───────────────┬──────────────────────────┬───────────────────┤
│ 左侧来源与筛选 │ 中间攻略聚合流           │ 右侧对比与推荐     │
│               │                          │                   │
│ 平台开关       │ 统一攻略卡片             │ 方案 A/B/C        │
│ 内容类型       │ 平台徽标 / 作者 / 时间   │ 评分雷达          │
│ 时间范围       │ 景点标签 / 证据摘要      │ 推荐理由          │
│ 排序           │ [查看来源] [加入对比]    │ 风险与冲突        │
│ 来源状态       │                          │ [采用此方案]      │
├───────────────┴──────────────────────────┴───────────────────┤
│ 底部：已选攻略 8 条 · 覆盖 2 个平台 · [上一步] [生成方案]      │
└──────────────────────────────────────────────────────────────┘
```

### 移动端

- 顶部折叠行程摘要；
- 平台筛选横向滚动；
- 攻略卡片单列；
- 对比方案用横向卡片/底部抽屉；
- 来源追溯使用全屏抽屉。

## 4. 页面模块

### 4.1 行程摘要与步骤条

显示：

- 城市、日期、天数、人数；
- 预算与是否含城际；
- 兴趣标签；
- 当前阶段与已完成阶段。

作用：让用户随时知道自己是在“收集”“对比”还是“生成”。

### 4.2 平台来源面板

每个平台一张状态卡：

| 字段 | 说明 |
|---|---|
| 平台 | 小红书 / 抖音 |
| 状态 | 可用 / 需授权 / 限流 / 无结果 / 失败 |
| 已采集 | 条数 |
| 最近采集 | 时间 |
| 覆盖类型 | 景点 / 路线 / 餐饮 / 避坑 |
| 操作 | 启用/停用、重新采集、查看失败原因 |

平台不可用时必须显式提示，不允许用其他平台数据冒充。

### 4.3 聚合进度

按平台展示：

```text
小红书  ✓ 12 条  00:08
抖音    ✓  6 条  00:11
```

并提供总进度和取消按钮。

### 4.4 统一攻略流

卡片统一字段：

- 标题与摘要；
- 平台徽标、作者、发布时间、采集时间；
- 景点标签、建议天数、预算区间；
- 适合人群/季节；
- 证据片段（原文引用，限制长度）；
- “查看来源”与“加入对比”。

支持筛选：

- 平台；
- 内容类型（路线/景点/美食/避坑）；
- 发布时间（7 天/30 天/不限）；
- 是否含具体景点；
- 是否与当前行程重复。

### 4.5 对比矩阵

按方案对比：

| 维度 | 方案 A 经典全覆盖 | 方案 B 轻松慢游 | 方案 C 小众深度 |
|---|---|---|---|
| 覆盖景点数 | 8 | 5 | 6 |
| 跨平台共识 | 高 | 中 | 低 |
| 预算匹配 | 92% | 98% | 85% |
| 路程强度 | 高 | 低 | 中 |
| 新鲜度 | 近 30 天 | 近 90 天 | 近 30 天 |
| 风险提示 | 周一闭馆 | 少 | 交通不便 |

每个单元格可点开来源依据。

### 4.6 推荐方案面板

每个方案包含：

- 方案名与一句话定位；
- 综合分与分项得分；
- 3–5 条推荐理由；
- 风险/冲突；
- 来源数量与平台分布；
- “采用此方案”。

推荐理由必须带来源编号，例如：

```text
① 2 个平台共 5 篇攻略提到“博物院—总统府—玄武湖”顺路
   [小红书 S12] [抖音 S03]

② 与你的“历史文化 + 美食”偏好匹配度 91%
   [小红书 S12] [抖音 S03]

③ 近期攻略提示周一闭馆，已自动避开
   [小红书 S18]
```

### 4.7 来源追溯抽屉

点击任意来源/理由打开：

- 平台、标题、作者、发布时间、采集时间；
- 原始链接；
- 结构化结论；
- 证据片段（限定长度）；
- 互动数据（若平台提供）；
- 该来源影响了哪些行程项；
- 冲突提示；
- “标记不相关”。

### 4.8 最终行程预览

展示：

- 每日景点顺序；
- 交通与用时；
- 餐饮/住宿建议；
- 预算汇总；
- 每个条目的来源徽标；
- “生成完整行程”按钮。

## 5. 数据模型

### SourceRecord

```json
{
  "source_id": "xhs:S12",
  "platform": "xiaohongshu",
  "url": "https://...",
  "author": "...",
  "title": "...",
  "published_at": "2026-10-01",
  "fetched_at": "2026-10-30T17:00:00+08:00",
  "excerpt": "……",
  "engagement": {"likes": 1200, "comments": 86},
  "status": "ok"
}
```

### GuideClaim

```json
{
  "claim_id": "C-001",
  "source_id": "xhs:S12",
  "type": "poi|route|duration|budget|tip|season",
  "value": "南京博物院建议 3 小时",
  "evidence": "……原文片段……",
  "confidence": 0.86
}
```

### GuideCluster

```json
{
  "cluster_id": "POI-NJ-MUSEUM",
  "canonical_name": "南京博物院",
  "aliases": ["南京博物院", "南博"],
  "location": {"longitude": 118.825, "latitude": 32.041},
  "source_ids": ["xhs:S12", "douyin:S03"],
  "agreement_count": 3,
  "conflicts": ["周一闭馆，部分攻略未提"]
}
```

### PlanCandidate

```json
{
  "plan_id": "A",
  "title": "经典全覆盖",
  "items": [],
  "score": 87.5,
  "score_breakdown": {
    "evidence": 22,
    "consensus": 18,
    "freshness": 13,
    "feasibility": 14,
    "budget": 9,
    "preference": 9,
    "diversity": 5
  },
  "reasons": [],
  "source_refs": ["xhs:S12", "douyin:S03"]
}
```

## 6. 平台适配器

所有平台实现同一接口：

```python
async def fetch(query: GuideQuery) -> list[SourceRecord]
```

### 小红书

- 复用现有 `xhs_service` 的签名搜索与笔记详情；
- 需要有效 Cookie；
- 遵守平台频率限制，失败不重试风暴。

### 抖音

- 优先使用官方开放平台/授权接口；
- 或支持用户粘贴公开分享链接，解析标题与页面元信息；
- 不建议用 Cookie 批量抓取，避免风控与合规风险；
- 未配置时显示“需授权/未接入”。

### 统一状态

```text
ok / empty / need_auth / rate_limited / timeout / failed
```

单平台失败只降低来源覆盖度，不终止整个流程。

## 7. 筛选与评分

### 7.1 硬约束

- 城市/日期可行；
- 用户“想去”的景点优先纳入；
- 预算上限；
- 老人/儿童/体力限制；
- 闭馆日、预约要求。

### 7.2 综合分（100）

| 维度 | 权重 | 说明 |
|---|---:|---|
| 证据覆盖 | 25 | 有多少行程项有真实攻略支撑 |
| 跨平台共识 | 20 | 同一景点/路线被多少平台提及 |
| 新鲜度 | 15 | 发布时间与采集时间的衰减 |
| 可执行性 | 15 | 路程、开放时间、预约、体力 |
| 预算匹配 | 10 | 与用户预算的偏差 |
| 偏好匹配 | 10 | 与兴趣标签/特殊需求匹配 |
| 来源多样性 | 5 | 平台分布，避免单一平台偏见 |

### 7.3 去重与冲突

- 同一景点跨平台合并为一个 `GuideCluster`；
- 来源数量不直接等于可信度，需结合新鲜度和证据具体性；
- 冲突信息（闭馆日、票价、预约）单独展示，不静默选一个；
- 无来源支撑的条目标记“通用建议”，不能标成“平台推荐”。

## 8. 推荐理由与可溯源性

每个推荐理由必须包含：

```text
reason_text
source_ids
evidence_snippets
confidence
```

禁止只输出“根据攻略推荐”而不给来源。

示例：

```json
{
  "reason": "2 个平台共 5 篇攻略提到这条路线顺路，且与你偏好的历史主题一致",
  "source_ids": ["xhs:S12", "douyin:S03"],
  "evidence_snippets": ["博物院出来步行到总统府很近……"],
  "confidence": 0.88
}
```

## 9. 页面状态

- 首次加载：平台卡逐个进入“采集中”；
- 部分成功：显示成功平台结果，失败平台可重试；
- 全部失败：显示原因与“仅用通用建议生成”；
- 无结果：建议放宽关键词/日期/平台；
- 来源失效：标记“链接可能失效”，保留摘要；
- 生成中：锁定对比页操作，显示当前阶段；
- 用户取消：保留已采集来源，可稍后继续。

## 10. 验收标准

1. 两个平台均有独立状态，失败可定位；
2. 每条攻略有平台、作者、时间、链接；
3. 同一景点跨平台只出现一个主卡片，但来源可展开；
4. 每个方案有分项评分和至少 3 条带来源的推荐理由；
5. 每个行程项可追溯到来源或明确标记“通用建议”；
6. 平台不可用时不伪造来源；
7. 移动端可完成来源筛选、对比、采用方案；
8. 生成失败可回到对比页，不丢已采集数据。

## 11. 实施分期

### P0：可用的聚合骨架

- 小红书适配器；
- 统一 SourceRecord/GuideClaim；
- 来源追溯抽屉；
- 三方案对比 + 评分；
- 单平台失败隔离。

### P1：抖音接入

- 官方 API 或公开链接解析；
- 平台状态与授权提示；
- 跨平台去重与冲突检测。

### P2：体验优化

- 来源可信度学习；
- 用户反馈“不相关”；
- 方案收藏与历史对比；
- 导出时附来源附录。
